## 0. What changes, in one paragraph

Today a Findings report is produced by a chain of session scripts: a hand-written scenario builder per architecture, a data script that evaluates, allocates and decomposes (≈ 160 s for 4 architectures × 4 scales), a pruning script over a 23-mechanism Shapley study, and a bilingual HTML builder over a shared kit. v5 turns that chain into a HAC-D feature: the user supplies three input records — a **topology record**, a **failure-rate override**, a **mechanism parameter set** — plus the scales and the target, and `hac-d findings` (later the web app) produces the same report with no code change. The numerical core stays deterministic and LLM-free; every new primitive gets golden vectors computed independently; the v4.4 reports must regenerate from the new pipeline to the number.

## 1. What the user supplies

### 1.1 Topology record (`TopologyRecord`, JSON, zod-validated)

```jsonc
{
  "id": "ubl128", "name": { "zh": "SuperPoD Flex / UBL128（128 NPU，单层 UB 交换）", "en": "SuperPoD Flex / UBL128 (128 NPUs, single-layer UB switch)" },
  "template": "a950-ub2",                       // built-in template, or "custom" with the full superpod geometry below
  "superpod": { "preset": "atlas950-1k", "computeRacks": 2, "commRacks": 1, "rackSwitches": 0, "podUplinksPerNpu": 4, "podSwitchRadix": 128 },
  "countOverrides": { "commCabinet": { "count": 1, "npus": 512 }, "ubMeshLink": { "count": 28, "npus": 8 } },
  "scaleOut": { "portsPerNpu": 4, "planes": 4, "radix": 1024, "oversubscription": 1, "transceiversPerLink": 2 },
  "variants": [ { "id": "twoPlane", "name": { "zh": "2 平面 × 两层，radix 1,024", "en": "2 planes × 2 tiers, radix 1,024" }, "scaleOut": { "portsPerNpu": 2, "planes": 2, "radix": 1024, "oversubscription": 1, "transceiversPerLink": 2 }, "basis": { "zh": "950 白皮书 2 × 400G UBoE", "en": "950 white paper 2 × 400G UBoE" } } ],
  "layers": {                                   // the instance of each layer, for MTBF per instance and the overlay
    "superpod": { "unit": "supernodes", "npus": 128 }, "cabinet": { "unit": "racks", "npus": 64 }, "node": { "unit": "nodes", "npus": 8 }
  },
  "provenance": { "superpod.computeRacks": { "source": "Huawei Computing 2026-09-30", "confidence": "vendor" }, "superpod.podSwitchRadix": { "source": "derived from 4 × 800G per NPU", "confidence": "derived" } },
  "assumed": [ "2 compute cabinets of 64 NPUs per pod", "one switch cabinet per 4 pods" ]
}
```

What exists: the `superpod`, `scaleOut` and `countOverrides` shapes are the scenario schema's own; `topologyScenario(template, N, patch)` builds the scenario. What is new: the record as a file with `variants`, `layers` and `provenance`; the loader `scenarioFromRecord(record, N, variantId?)`; built-in records for the four current architectures (`records/native950.json`, `ubl128.json`, `cm384.json`, `a3server.json`) so that `scenarioFromRecord(native950, 500000)` equals today's `scenarioOf('native', 500000)`. A topology that introduces a unit kind absent from the fault-unit list (an optical engine, an NPO module) needs a unit-library entry and a BOM row — one documented extension point, not a special case.

### 1.2 Failure-rate override (`FaultRateOverride`, JSON)

```jsonc
{
  "basis": "per-unit",                          // per-unit (HAC-D) or per-card (ReMAP)
  "rates": {
    "FABRIC-hard":  { "unit": "ub-switch", "fit": 57.1, "source": "catalog FABRIC via CM384 geometry", "confidence": "derived" },
    "OPT-hard":     { "unit": "ub-link",   "fit": 4.8,  "source": "catalog OPT via CM384 geometry",    "confidence": "derived" },
    "POWER-hard":   { "unit": "cabinet",   "fit": 8533.3 * 0.6, "source": "fleet measurement 2026-Q4", "confidence": "measured" }
  },
  "analogues": { "FABRIC-hard@roce": "FABRIC-hard", "OPT-hard@roce": "OPT-hard" }   // scale-out units take the UB values unless given
}
```

What exists: `unitFaultLibrary()` (catalog → unit through the CloudMatrix384 geometry), `library.json` records with provenance, per-component values inside a scenario. What is new: the override file and `applyFaultRates(scenario, override)`; the confidence tag of every overridden class carried into the report tables (`span.cf` already prints it).

### 1.3 Mechanism parameter set (`MechanismSet`, JSON)

```jsonc
{
  "id": "remap-latest-2026-10", "source": "ReMAP f53ab7e, extensionScenario() + parameter sets",
  "baseline": ["D-SDC", "R-SDC", "R-REPLAY", "R-PROCESS", "R-ELASTIC", "C-FAST"],
  "candidates": ["D-HARD", "D-RECOVERY-CLASSIFY", "R-LINK-LOCAL", "R-RUNTIME-SNAPSHOT", "H-CONTROL-CONTINUITY", "C-LOSSLESS", "R-FABRIC-DEGRADE"],
  "goodputOnly": ["D-SDC-FP8", "D-SDC-FP4", "D-ABFT", "D-NET-SDC", "H-SDC-SCREEN"],
  "parameters": { "R-LINK-LOCAL": { "successSeconds": 2, "eligibleShare": 1, "success": 0.95 }, "R-RUNTIME-SNAPSHOT": { "startupTargetSeconds": 15, "eligibleShare": 0.95 } },
  "efforts": { "R-LINK-LOCAL": 3 },
  "levers": [ { "id": "auto", "limit": 60, "effort": 3 }, { "id": "success", "limit": 0.999, "effort": 3 }, { "id": "manual", "limit": 1800, "effort": 2 } ],
  "derate": { "coverageDelta": 0.05, "successDelta": 0.08, "timeFactor": 1.5, "reductionFactor": 0.5 },
  "metadata": { "R-LINK-LOCAL": { "deploy": "superpod", "acts": ["superpod", "scaleout", "npu"], "stage": "rung" } }
}
```

What exists: `MECHANISM_LIBRARY` + the audit library with defaults and overlap rules; `REMAP_LATEST_PARAMS` as a script constant; deploy / acts / stage in `ascend-mechanism-hierarchy.ts`. What is new: the set as a file, `applyMechanismSet(library, set)`, `metadata` on `MechanismDef`, and `pruneByShapley` producing the `candidates` / `goodputOnly` lists from a study when the user does not fix them by hand.

### 1.4 Run options

`{ scales: [10000, 100000, 200000, 500000], target: 0.985, window: { trials: 400, seed: 1, required: 0.9 }, shapley: { permutations: 300 }, hardwareSplit: "arinc", effortPerHalving: 2, floor: 0.05 }` — all exist as options of `allocateStrategy`, `allocationStudy` and `buildLedgerRun`; v5 collects them in one validated object that the report footer echoes.

## 2. Pipeline and the core modules to build

| Step | Module | Today's code (moves from) | Interface |
|---|---|---|---|
| Evaluate in MTBF / MTTR form | `evaluate` output `kpiForm` | `kpi()` in `scripts/scaling-common.ts` | `kpiForm(scenario) → { aOp, aRun, phi, lamHw, mtbfHwH, mttrS, sumLP, other[], F }`; classes apart; closure against the running fraction asserted |
| Layer model | `packages/core/src/layers/` | `LAYERS`, `levels()`, `instancesOf()` in `ascend-allocation-data.ts` | `layerModel(record) → LayerDef[]`; `byLayer(scenario, layers) → { lam, c, iso, sdc, mttrS, instances, mtbfInstanceH, rows }[]` |
| MTTR decomposition | `packages/core/src/mttr/decompose.ts` | `chainSplit()` (custom rungs, failed-rung time) + `mttrSplit()` with `automaticStages` | `mttrDecomposition(scenario) → { mttrS, contrib, probs, stages, recovery }`, rate-weighted, closes on the engine's mean pause per class |
| Requirement | `strategy/requirement.ts` | `required` block of `ascend-allocation-data.ts` | `requirement(scenario, target) → { B, mtbfAtTodayMttrH, mttrAtTodayMtbfS, factors }` on the derated design |
| Recommendation with the window rule | `allocateStrategy` option `windowRule` | `recommendPlan()` / `recommendDesign()` in `scaling-common.ts` | `{ trials, seed, required: 0.9, escalate: 'cheapest-move' }` → the plan that passes the window check, the largest supported uniform factor k, the escalation trace |
| Mechanism pruning | `study/prune.ts` | `ascend-mechanism-hierarchy.ts` | `pruneByShapley(study, { threshold: 0.0015, dominated: {…} }) → verdict per mechanism` (reference / candidate / goodput / pruned / capability) |
| Per-layer attribution | `study` output | `shapleyByLevel()` in `a950-level-allocation.ts` | exact Shapley per layer for ≤ 8 players, added to `allocationStudy` |
| Hierarchical budget | `packages/core/src/budget/` | the per-size block of `ascend-allocation-data.ts` (today, required, hardware-only, optimal, recommended, decomposition, removal) | `hierarchicalBudget(scenario, options) → BudgetResult` = the `results.json` shape for one architecture × one scale |
| Topology variants and BOM | `topology` | `ascend-bom-100k.ts` | `bomOfVariants(record, N) → Design[]`, with the identity checks the BOM builder performs (same family ⇒ same scale-out counts; parts sum to the total) |

Script code that stays script code: the Ascend-specific scenario builders disappear into records (§1.1); `shapley-figure.mjs` and the scaling-report builders stay as they are until the reports package (§4) absorbs them.

## 8. Acceptance criteria (whole phase)

1. `hac-d findings --record ubl128` regenerates `docs/ASCEND_ALLOCATION_FINDINGS_UBL128.html` with identical numbers and page layout (date aside) — the only numerical differences allowed are below 1e-9 relative.
2. A new record with a template the engine already knows (Atlas 960E, `a960e-ub`) produces Methodology-consistent Findings pages, BOM rows and the overlay figure with no code change; a record with a new unit kind fails with a message naming the two extension points.
3. A failure-rate override with `confidence: measured` on one class shows that tag in Table 3 and changes exactly that class's rows.
4. A mechanism set that removes one candidate changes the candidate count in the Methodology hierarchy figure and the plan tables, and nothing else.
5. `npm test` passes with the new goldens; `reference-compare` is unchanged.
6. Every report still prints its 口径 notes and formula references; no event classes are added anywhere (test on `kpiForm`).

## 9. Risks and standing assumptions

- The failure-rate basis is an analogue prior from GPU fleets converted per unit through the CloudMatrix384 geometry; the pipeline must keep confidence tags visible in every table, and a measurement plan (fleet data per unit class) should precede decisions above 200k.
- Automatic-recovery stages are equal thirds unless a startup / read-stage mechanism is in the design; a measured stage split belongs in the mechanism set (`stages` field) — add it to the schema in T3 so the data model does not need a second change.
- Sampled Shapley (300 permutations) has a half-width up to 0.25 pt at 500k; the pruning threshold (0.15 pt) sits above it, but borderline verdicts (R-FABRIC-DEGRADE) should be re-checked whenever parameters change — `hac-d prune` makes that a one-line rerun.
- The window rule escalates by the cheapest unused move; with more than 10 moves the exact optimal search falls back to the greedy path — the report must say which path produced the plan (a note already exists in `allocateStrategy`).
- The reproduction test pins today's numbers; any intentional model change afterwards must update the goldens through the Python path, never by editing expected values.
