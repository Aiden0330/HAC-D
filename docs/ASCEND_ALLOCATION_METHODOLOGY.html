昇腾集群有效 goodput 分配：方法

目标有效 goodput G_eff ≥ 98.5 %（30 天窗口、一个同步训练作业；交付 goodput 并列报告）在 1 万–50 万卡、四种拓扑上的分配方法：HAC-D 单元口径的失效率、ReMAP 机制集的分层与取舍、MTBF / 每次中断损失的逐层预算与三重校核。结果见各拓扑的 Findings 文件与 BOM 表。

1. 范围与口径

  • 目标：一个同步训练作业在 30 天窗口上的有效 goodput G_eff ≥ G* = 98.5 %——检查点模型（保存 δ/τ、每次回滚的重算、恢复暂停）乘吞吐系数（亚健康降速、局部损失、备机阻塞、机制开销），静默损坏的事件暂停计入停机；名义参数、全部机制降额（覆盖 −5 pt、成功 −8 pt、时间 ×1.5、发生率改善 ×0.5）与逐窗口（400 个窗口，Wilson 95 % 下界 ≥ 90 %）三重满足；表中给出降额值（验收口径）。交付 goodput G_del（再减去未检出静默损坏的损失）并列报告，不作为验收条件；A_op（运行时间份额，公式 1）仍可在侧车数据中查到。
  • 失效率口径：HAC-D 单元口径——ReMAP / ai-cluster-reliability 的 54 类事件目录按 CloudMatrix384 几何换算到每个硬件单元（NPU、CPU、节点、计算柜、UB 交换芯片、UB 光链路、作业级），再乘各拓扑自己的单元数；跨超节点网络的交换机与光链路用 UB 单元的类比值（@roce，置信度 assumed）。每类事件只归一个单元、一个层级。失效率覆盖记录（FaultRateOverride）可按单元或按卡替换任一类的值并带入其置信度。
  • 事件类不相加：硬中断（经机制链）、亚健康隔离、静默损坏检出与漏检、误报各自保留速率与暂停；A_op 的分母是集群·小时。
  • 机制集：ReMAP 的六个参考机制（D-SDC、R-SDC、R-REPLAY、R-PROCESS、R-ELASTIC、C-FAST）在每个设计的基线里；ReMAP 最新扩展按第 4 节的规则分层取舍，七个 G_eff 候选进入分配；R-CKPT / R-MANUAL 以三个恢复杠杆参与（自动尝试 ≥ 60 s、自动成功 ≤ 99.9 %、人工 ≥ 30 min）。
  • 拓扑：华为原生 Atlas 950 超节点（1,024 NPU）、SuperPoD Flex / UBL128（128 NPU，单层 UB 交换）、Atlas 900 A3 超节点 / CloudMatrix384（384 NPU，两级 UB 交换）、Atlas 800T A3 服务器集群（8 NPU / 台，跨机 RoCE）（UB 域 = 8 NPU）；几何与假设见 BOM 表与各记录的 provenance 字段。

4. ReMAP 机制集：分层与取舍

ReMAP 的 8 个原始机制与 15 个最新扩展（加 I-CONTAIN 能力）按部署层、作用层与所改变的量归类；取舍用四种拓扑上 23 个机制的 Shapley 值（裸架构、300 个置换）：

规则：参考集原样保留；同一恢复阶段上被更短机制支配的剪除（同阶段取最小值，不相加）；其余在 50 万卡上四种拓扑的有效 goodput Shapley 均 ≥ 0.15 个百分点 → G_eff 候选（进入分配），交付 goodput Shapley 均 ≥ 0.15 点 → 只保交付 goodput（设计中保留，不参与 G_eff 分配），否则剪除。机制集记录带有结论与理由，hacd prune 按同一规则重算。

结果：7 个 G_eff 候选（D-HARD、R-LINK-LOCAL、H-CONTROL-CONTINUITY、R-RUNTIME-SNAPSHOT、C-ASYNC、C-LOSSLESS、D-RECOVERY-CLASSIFY）、5 个只保交付 goodput（D-SDC-FP8、D-SDC-FP4、D-ABFT、D-NET-SDC、H-SDC-SCREEN）、5 个剪除（R-WARM-PROCESS、R-CANN-GRAPH 被 R-RUNTIME-SNAPSHOT 支配；D-SLOW、R-FABRIC-DEGRADE、R-HCCL-ELASTIC 低于阈值）、1 个能力（I-CONTAIN）。7 个候选 + 3 个杠杆 = 10 个动作，HAC-D 最优策略精确枚举 1,024 个子集。

机制集的表格——每项机制的部署层、作用层、所改变的量、努力、结论与理由，以及在该拓扑各规模上的 G_eff Shapley 与 50 万卡的交付 goodput Shapley（裸架构场景、300 次置换）——是各拓扑 Findings 文件的表 6；结论对四种拓扑相同。

重叠规则（审核库）：启动阶段的三个机制逐事件取最小值（按资格份额求期望）；D-RECOVERY-CLASSIFY 与“自动成功率”杠杆作用于同一概率，取两者中较高者，降额时前者的人工概率与杠杆的失败概率都 ×1.5（杠杆 99.9 % → 99.85 %）；检测机制降额后不低于它替代的基线检测；R-HCCL-ELASTIC 需要 R-ELASTIC；静默检测器按残余漏检复合。

5. MTBF / MTTR 的逐层预算与叠加图

  • 系统级（公式 1′–2′）：今天的 MTBF_hw、每次中断损失 R_eff、有效 goodput G_eff 与交付 goodput G_del（降额）；要求 B；两个端点“今天 R_eff 下需要的 MTBF”“今天 MTBF 下允许的 R_eff”；推荐设计的 MTBF_hw / R_eff / G_eff / G_del（降额）。
  • 层级（公式 3′）：每层的 λ_ℓ、暂停 t̄_ℓ、重算、损失 r_ℓ、U_ℓ 与按实例的 MTBF（降额），今天 → 推荐设计；杠杆与机制改变 r_ℓ，硬件系数 k 改变 λ_ℓ；检查点保存与吞吐系数作为单独的行。
  • 硬件单元（公式 4）：每类单元的数量、今天 FIT → 允许 FIT（× k）、单元 MTBF 与对集群中断率的份额——交付与验收值；失效率覆盖替换的类带其置信度标签。
  • 机制参数（公式 5）：推荐设计中每个机制的名义参数（即要求）与降额核验值；MTTR 按梯级与阶段的构成；每个机制去掉的暂停按层。
  • 叠加图：各拓扑的 Findings 文件把这些预算叠在硬件层级图上——每层一张卡片，四个规模各一行：允许的实例 MTBF、层 MTTR、U_ℓ 预算、k，以及部署在该层的机制。

流程：① 目标与口径（G_eff ≥ G*）→ ② 总预算 B（公式 2′，暂停 + 重算）→ ③ 按故障单元分到六层 → ④ 层内取舍：候选机制 + 恢复杠杆 + 硬件 ARINC，总努力最小 → ⑤ 校核：名义、降额、逐窗口（不支持则加最便宜的未用动作或收紧 k；全部动作仍不可达时报告上限）→ ⑥ 输出：系统 / 层 / 单元 / 机制四级预算。

Ascend cluster effective-goodput allocation: methodology

How the goal effective goodput G_eff ≥ 98.5 % (30-day window, one synchronous training job; the delivered goodput reported beside it) is allocated at 10k–500k NPUs on four topologies: HAC-D’s per-unit failure rates, the ReMAP mechanism set categorised and pruned, hierarchical MTBF / loss-per-interruption budgets and the three checks. Results are in the per-topology Findings files and the BOM table.

1. Scope and 口径

  • Goal: effective goodput G_eff ≥ G* = 98.5 % for one synchronous training job over a 30-day window — the checkpoint model (saves δ/τ, recompute per rollback, recovery pauses) times the throughput factors (sub-health slowdown, local loss, blocked spares, mechanism overhead), the episode pauses of silent corruption counted as downtime; met nominally, with every mechanism derated (coverage −5 pt, success −8 pt, times ×1.5, rate improvements ×0.5) and window by window (400 windows, Wilson 95 % lower bound ≥ 90 %); the tables show the derated values (the acceptance 口径). The delivered goodput G_del (less the undetected silent-corruption loss) is reported beside it, not an acceptance condition; A_op (the running share, formula 1) stays in the sidecar data.
  • Failure-rate basis: HAC-D per unit — the 54-event ReMAP / ai-cluster-reliability catalog converted to each hardware unit (NPU, CPU, node, cabinet, UB switch chip, UB optical link, job level) through the CloudMatrix384 geometry, then multiplied by each topology’s own unit counts; scale-out switches and links use the UB units’ analogue values (@roce, confidence assumed). Every event class belongs to exactly one unit and one layer. A failure-rate override record replaces any class per unit or per card and carries its confidence into the tables.
  • Event classes stay apart: hard interruptions (through the mechanism chain), isolation of sub-healthy units, detected and undetected silent corruption and false alarms each keep their own rate and pause; the denominator of A_op is the cluster-hour.
  • Mechanism set: ReMAP’s six reference mechanisms (D-SDC, R-SDC, R-REPLAY, R-PROCESS, R-ELASTIC, C-FAST) are in every design’s baseline; the latest ReMAP extensions are categorised and pruned by the rule of Section 4, seven G_eff candidates enter the allocation; R-CKPT / R-MANUAL take part as three recovery levers (automatic attempt ≥ 60 s, automatic success ≤ 99.9 %, manual ≥ 30 min).
  • Topologies: Huawei native Atlas 950 SuperPoD (1,024 NPUs), SuperPoD Flex / UBL128 (128 NPUs, single-layer UB switch), Atlas 900 A3 SuperPoD / CloudMatrix384 (384 NPUs, two-level UB switching), Atlas 800T A3 server cluster (8 NPUs per server, RoCE between servers) (UB domain = 8 NPUs); geometry and assumptions in the BOM table and each record’s provenance field.

4. The ReMAP mechanism set: hierarchy and pruning

ReMAP’s 8 original mechanisms and 15 latest extensions (plus the I-CONTAIN capability) are categorised by deployment layer, the layers they act on and the quantity they change; pruning uses the Shapley values of the 23 mechanisms on the four architectures (bare architecture, 300 permutations):

Rule: the reference set stays; a mechanism dominated by a shorter one on the same recovery stage is pruned (minimum on a stage, never the sum); otherwise effective-goodput Shapley ≥ 0.15 pt at 500k on every architecture → G_eff candidate (enters the allocation), delivered-goodput Shapley ≥ 0.15 pt → delivered-only (kept in the design, outside the G_eff allocation), else pruned. The mechanism-set record carries the verdicts and reasons; hacd prune re-derives them by the same rule.

Outcome: 7 G_eff candidates (D-HARD, R-LINK-LOCAL, H-CONTROL-CONTINUITY, R-RUNTIME-SNAPSHOT, C-ASYNC, C-LOSSLESS, D-RECOVERY-CLASSIFY), 5 delivered-only (D-SDC-FP8, D-SDC-FP4, D-ABFT, D-NET-SDC, H-SDC-SCREEN), 5 pruned (R-WARM-PROCESS, R-CANN-GRAPH dominated by R-RUNTIME-SNAPSHOT; D-SLOW, R-FABRIC-DEGRADE, R-HCCL-ELASTIC below the threshold), 1 capability (I-CONTAIN). 7 candidates + 3 levers = 10 moves, which HAC-D’s optimal strategy enumerates exactly (1,024 subsets).

The set’s table — each mechanism’s deployment layer, layers acted on, quantity changed, effort, verdict and reason, with the G_eff Shapley values per scale and the delivered goodput Shapley at 500k on that architecture (bare scenario, 300 permutations) — is Table 6 of each Findings page; the verdicts are the same for the four topologies.

Overlap rules (audit library): the three startup-stage mechanisms take the minimum per event (the expectation over their eligible shares); D-RECOVERY-CLASSIFY and the automatic-success lever act on the same probability and the higher one applies, derated the former’s manual probability and the lever’s failure probability both ×1.5 (the lever 99.9 % → 99.85 %); a derated detector never falls below the baseline detection it replaces; R-HCCL-ELASTIC needs R-ELASTIC; silent-corruption detectors compound on the residual misses.

5. Hierarchical MTBF / MTTR budgets and the overlay

  • System (formulas 1′–2′): today’s MTBF_hw, loss per interruption R_eff, effective goodput G_eff and delivered goodput G_del (derated); the requirement B; the two ends “MTBF needed at today’s R_eff”, “R_eff allowed at today’s MTBF”; the recommended design’s MTBF_hw / R_eff / G_eff / G_del (derated).
  • Layer (formula 3′): each layer’s λ_ℓ, pause t̄_ℓ, recompute, loss r_ℓ, U_ℓ and MTBF per instance (derated), today → recommended design; levers and mechanisms move r_ℓ, the hardware factor k moves λ_ℓ; the checkpoint saves and the throughput factors are separate lines.
  • Hardware unit (formula 4): count, today’s FIT → allowed FIT (× k), unit MTBF and share of the cluster interruption rate — the delivery and acceptance values; classes replaced by a failure-rate override carry their confidence tag.
  • Mechanism parameters (formula 5): each mechanism’s nominal parameters (the requirement) and derated check values in the recommended design; the MTTR composition by rung and stage; the pause each mechanism removes, by layer.
  • Overlay: each topology’s Findings file lays these budgets over the hardware hierarchy — one card per layer, one row per scale: allowed MTBF per instance, layer MTTR, U_ℓ budget, k, and the mechanisms deployed on that layer.

Procedure: ① goal and 口径 (G_eff ≥ G*) → ② total budget B (formula 2′, pause plus recompute) → ③ split over six layers by fault unit → ④ within a layer: candidate mechanisms + recovery levers + ARINC hardware at least total effort → ⑤ checks: nominal, derated, per window (if unsupported, add the cheapest unused move or lower k; when every move still falls short, report the ceiling) → ⑥ outputs: budgets at the system / layer / unit / mechanism levels.

Is a model-agnostic Agent module required?

Verdict: not required to produce these tables and models — the chain above is deterministic and reproducible, and should stay LLM-free. Recommended as an optional module for three jobs: extracting parameters from surveys, papers and product pages (with provenance and confidence), authoring or rewriting scenarios and design variants from natural language (schema-validated JSON out), and writing bilingual narrative and review checklists; today these three jobs are done by skills in Claude Code sessions (allocate-to-target, model-check, scenario-review), not inside the product.
