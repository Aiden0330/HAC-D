自顶向下：从可用度目标到硬件 MTBF 与机制 MTTR

口径：作业运行可用度 A_op（30 天窗口内的运行时间占比），目标为方案默认的 98.5 %；主算例为 A3 · CloudMatrix384 拓扑、默认六项机制，内置规模 10k / 100k / 200k / 500k NPU（A2、Atlas 950 与 Atlas 960E 的要求见第 2 节）。设计须在降额参数（覆盖率 −5 pt、成功率 −8 pt、时间 ×1.5）下达标，因此要求按降额设计计算。FIT 为参考目录先验（假设）按 CloudMatrix384 几何换算到各硬件单元。每个数字都由 scripts/mtbf-mttr-topdown.ts 在引擎上计算，公式与引擎的运行占比逐项相等（误差 < 10⁻⁹）。

1. 自顶向下公式

① 单一事件类（经典）：
A = MTBF / (MTBF + MTTR)
② 作业级：每个事件类 k 用自己的 MTBFₖ 与 MTTRₖ（不同事件类不合并成一个 MTBF），静默错误的事件暂停单独计为 φ_SDC：
A_op = (1 − φ_SDC) / (1 + MTTR_hw/MTBF_hw + Σₖ MTTRₖ/MTBFₖ)
③ MTBF 层：硬件中断的作业级 MTBF 由各硬件单元的 MTBF 与数量 nᵤ(N) 合成：
1 / MTBF_hw = Σᵤ nᵤ(N) / MTBFᵤ , MTBFᵤ = 10⁹ / FITᵤ [h]
④ MTTR 层：每次硬件中断的平均暂停 = 各类按事件率加权，每类沿机制链（网络切换 → 重执行 → 弹性 → 进程 → 全局恢复）求期望：
MTTR_hw = Σᵢ (λᵢ/λ_hw) · Σ_path P(path) · T(path) ; T(global) = t_det + Σ t_fail + t_auto + (1 − s)·t_manual ; t_det = c·t_fast + (1 − c)·t_timeout
⑤ 要求（MTBF_hw 以小时、MTTR 以秒计）：
MTTR_hw / MTBF_hw ≤ B , B = 3600·((1 − φ_SDC)/A* − 1) − F , F = Σₖ 3600·MTTRₖ/MTBFₖ [s/h]
⇒ MTBF_hw ≥ MTTR_hw / B 或 MTTR_hw ≤ B · MTBF_hw

MTBFᵤ = 10⁹ / FITᵤ 小时 ÷ 8,760；FITᵤ 为该单元上全部故障类的中断 FIT 之和（业务影响口径）。占比 = nᵤ·FITᵤ / Σ。500k 推荐分配的作业级结果：MTBF_hw 0.707 h (42.4 min)（现状 0.591 h (35.5 min)）。

怎样用作硬件指标：把“最低 MTBF（年 / 单元）”作为该单元的验收值；同一单元若有多个故障类，按各类 FIT 分到供应商（例如机柜：供电与液冷）。仅硬件方案在 500k 要求 NPU 99.5 年、机柜 95.2 年、作业级服务 2,910 年（现状 68.1 / 13.4 / 210 年），推荐分配则让 NPU 保持现状，只要求机柜 23.0 年、作业级服务 738 年、节点 29.1 年——其余由 MTTR 承担（第 4 节）。

总结（A3 · CloudMatrix384，A_op ≥ 98.5 %）：要求是 MTTR_hw / MTBF_hw ≤ B ≈ 46–55 秒/小时。10k 与 100k 用默认六项机制即可（MTTR 104 s，MTBF_hw 29.7 / 2.96 h）；200k 把自动尝试缩到 60 s，MTTR_hw 降到 75.1 s 即可，不需改硬件；500k 需要 MTBF_hw 0.707 h (42.4 min) 且 MTTR_hw 35.8 s（降额）：硬件上机柜 ≥ 23.0 年、作业级服务 ≥ 738 年、节点 ≥ 29.1 年；机制上检测 ≈ 1 s（D-HARD）、网络切换（R-NETFAIL）、自动尝试 60 s、人工 30 min。
注意：① MTBF 与 MTTR 之间的分配取工作量最小的组合（v4 最优）；工作量分数是假设，改变分数会改变分配（例如 200k 时仅硬件也可，工作量 5.19 对杠杆 3）。② 机制参数按机制库取值，不是求出的“最低需要值”；本文给出的是达到要求时各项参数的取值与它们承担的 MTTR。③ 隔离、已检出静默错误等事件类各有自己的 MTBF 与 MTTR，没有并入 MTBF_hw；它们决定预算 B 中的 F。④ 故障率为参考目录先验（假设），须以本集群实测替换。
