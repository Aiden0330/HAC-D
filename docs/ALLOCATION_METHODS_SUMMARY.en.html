Reliability allocation methods: fundamentals, formulas and algorithms

Allocation splits a system-level target (availability A*, goodput G*, failure rate λ*) top-down into an allowed failure rate per component class and a parameter setting per mechanism, then predicts bottom-up, verifies and iterates. 口径 rule: same event class, same denominator, same level; interruptions, sub-health and silent corruption are never added, each enters the window ledger on its own before anything is combined. The formulas match the HAC-D implementation (packages/core/src/allocation, study, mechanisms/plan); the three AGREE reports (REMAP_ALLOCATION_98P5_AGREE, MECHANISM_COMPARISON_98P5_AGREE, REMAP_LATEST_ALLOCATION_98P5_AGREE) are their worked examples on the 54-event catalog.

2. Algorithms (as implemented in HAC-D)

A · AGREE availability allocation and reallocation

  1. fixed = Σ non-domain pauses (sub-health isolation, detected silent corruption, predictor false alarms); U_free = (1 − A*) − fixed
  2. ptᵢ* = U_free · nᵢ / Σn; λᵢ* = ptᵢ* · 3600 / (A* · p̄ᵢ); kᵢ = λᵢ / λᵢ* (> 1 must improve); allowed FIT = current / kᵢ
  3. reallocation (water-filling): over = {kᵢ > 1}; repeat: rem = U_free − Σ_{i∉over} ptᵢ; drop any i ∈ over whose share rem·nᵢ/Σ_over n ≥ ptᵢ; until stable → k′ᵢ (the hardware task)
  4. closure check: scale every class to λᵢ / kᵢ and re-evaluate A_op with the engine, which must return A* (98.50 % in the examples)

B · Mechanism-set selection

  1. exact (≤ 10 candidates): enumerate 2ⁿ coalitions, min Σ effort s.t. V(nominal) ≥ target and V(derated) ≥ target; necessary mechanisms = intersection of all feasible coalitions; Pareto front effort–value
  2. greedy (> 10): add the mechanism with the largest ΔV / effort until the target holds nominally and derated
  3. AGREE two-phase: ① close the classes — score = [Σ_{i∈over} max(0, ptᵢ − max(ptᵢ^new, ptᵢ*)) − Δfixed] / effort; ② create slack — when the remaining over-budget classes have no closer, add mechanisms acting on the other classes by ΔA_op / effort; the reallocation hands their slack over
  4. derating DERATE_DEFAULT: coverage / eligible share −5 pt, success −8 pt, times and overheads ×1.5, reductions ×0.5; τ and domain counts are design choices and are not derated

C · Bottom-up prediction and verification

  1. closed form: 27-path recovery chain (predict → net-fail → replay → hot-swap → elastic → process → global) → class pauses p̄ᵢ → A_op; nine-line window ledger → delivered goodput
  2. Monte Carlo: 400 30-day window ledgers (one fault stream, mechanisms share the history) → P(window ≥ target), Wilson 95 % interval → supported / uncertain / below (≥ 90 % required)
  3. attribution: Shapley (exact up to 12 players, permutation sampling ± t half-width beyond); the allocation view uses the "removed over-budget excess" (single / last removed)
  4. closed loop: measured incidents → Garwood rate intervals (hacd rate) → write back FIT, stage times, detection coverage → rerun

3. Fundamentals

  • Conservation: Σᵢ ptᵢ + fixed = 1 − A_op with ptᵢ = A_run · λᵢ · p̄ᵢ / 3600. A method only changes how the budget is split between classes, the total is the same: ARINC scales every class alike, AGREE by complexity / importance / duty, Albert improves only the worst ones.
  • Two levers: hardware changes λᵢ (acceptance limit FIT = current / k), mechanisms change p̄ᵢ (a rung replaces the 264.5 s global recovery by a 5–60 s in-place one; detection, manual share and startup / read stage mechanisms act on every interruption). Classes with a rung gain slack, which the reallocation hands to POWER / COOL / MGMT / STORAGE / UNKNOWN that have none.
  • Complexity and importance decide AGREE's verdict: the reference catalog is normalised per card-hour → equal nᵢ → equal apportionment (100k cards: 13 / 18 classes over budget, CORE ×4.2, UNKNOWN ×3.7); counting physical units shrinks the rack-level budgets 256-fold (POWER ×188, STORAGE ×8400). In a synchronous job every hard interruption stops the job → Eᵢ = 1; every class is exposed over the whole window → tᵢ = T.
  • Screening laws: fault-free bound G ≤ τ/(τ+δ), a target above the bound of the best coalition is "proven unreachable"; scale laws: detection and recovery terms ∝ N, the checkpoint term ∝ √N, silent-corruption counts ∝ N, so allocate for the largest N that will run.
  • Worked numbers (54-event catalog, A_op ≥ 98.5 %): baseline holds up to 61k cards; AGREE sets reach 182k with ReMAP's original mechanisms, 378k with original + new, 373k with the latest ReMAP set; the 200k latest set gives 99.05 % (effort 27, P(window) 99.8 %); 500k has no feasible set and AGREE concentrates the hardware task on UNKNOWN ×2.4 / POWER ×1.31 / STORAGE ×1.05 (the other 15 classes untouched) where ARINC would demand ×1.40 on all of them.

How the cluster architecture shapes the allocation, and what to do next with the allocation components

AGREE's three weights (complexity n_i, importance E_i, duty t_i), the cluster-level event rate of every class and the mechanisms that can act on it are decided by the cluster architecture, not by the allocation method: the architecture fixes how many units each class has (countRule.per × topology → computeCounts), how many cards one event stops (blastRadius, ccf.beta, redundancy groups) and which rungs exist (component.mechanisms, elastic domains, hot spares, planes).
